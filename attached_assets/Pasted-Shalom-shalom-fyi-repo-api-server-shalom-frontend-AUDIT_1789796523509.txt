Shalom (shalom.fyi repo -- api-server + shalom frontend)

AUDIT ONLY -- make no code changes, no installs, no migrations, no commits, no pushes. Do not connect to the production database. Report findings only.

Audit the entire Shalom workspace (artifacts/api-server, artifacts/shalom, @workspace/db, Dockerfile, build scripts, Railway config). For every finding give: file path, line numbers, the verbatim code, severity (Critical / High / Medium / Low), and a concrete reproduction (the exact request or UI steps that trigger it). Do not state a cause you have not traced through the code -- if something is a symptom only, label it as a symptom and say what evidence would confirm the cause.

1. Inventory. List every server route (method + path + handler file:line) and every frontend page/component that calls the API. List every env var read anywhere (name, file:line, fallback value if any). Flag every hardcoded secret, URL, domain, model name, or magic number.

2. Auth / SSO. Trace the Bridget SSO flow end to end: token issuance consumed, signature verification (algorithm pinned or not, which secret, where it comes from), expiry check, return_to / redirect validation (open-redirect check), replay protection, logout and single-logout. Report what happens with an expired, tampered, or missing token.

3. Sessions. Paste the full session({...}) config. Report the store in use (MemoryStore or Postgres), the secret source and any fallback, and every cookie flag. List every read/write of req.session.

4. Access control -- enumerate the whole class. For EVERY route that touches a conversation, message, invite, verify, or mediation: state exactly what check confirms the caller is a participant of that conversation. Build a table: route | check present (yes/no) | check file:line | what a logged-in non-participant gets back. Include /verify. Any route missing the check is a finding.

5. Invites. Report: expiry (exists or not), consume-on-use, revocation, whether acceptance + participant-linking run in one transaction, and whether a DB-level unique constraint prevents a second acceptance or an overwrite of an existing partner. Describe what a double-click / two-tab race on acceptance does given the current code. Report whether a non-owner can mint an invite for someone else's conversation, and whether a user can accept an invite to their own conversation.

6. Hash chain. Report: exactly which fields are hashed and in what serialization (canonical or not), the genesis value, where prev_hash is read and written, and whether two messages inserted concurrently into one conversation can both link to the same prev_hash (fork). Report whether mediator (Bridget) messages and system/role events are in the chain. Report whether the chain is checked on conversation load or only on /verify. Report what /verify returns for a chain with a deliberately altered row (reason it through the code; do not modify data).

7. Mediation. Trace the mode = mediated path: how Bridget is called (URL, auth, secret), timeout, retry, error handling, what the user sees on failure, and whether a failed mediation call can leave a half-written message or a broken chain. Report whether mediation can be triggered on a conversation where the mode is not mediated.

8. Data layer. Paste the full Drizzle schema. Report every missing NOT NULL, foreign key, unique constraint, or index that the code assumes. Report the duplicate-creation guard: where it is, and whether it is app-level or DB-level. Report how the code handles an empty topic (list shows "No topic") and whether duplicate conversations can still be created by retry.

9. Frontend. Report: how messages are rendered (any dangerouslySetInnerHTML or unescaped HTML -- XSS check), whether messages and the conversation list refresh without logout/re-login (polling present or not, interval, cleanup on unmount), error states on failed create/send, loading/empty states, and any value displayed that is hardcoded rather than derived from data.

10. Build / deploy. Confirm the entry file Railway actually runs, whether every runtime dependency is bundled into dist (the Dockerfile ships dist only), CORS configuration, and any drift between dev and production config.

11. Duplication map. List every place the same constant, domain list, model name, or logic is defined more than once (client and server included).

12. Tests. List existing tests and what they cover; list which of the findings above have no test.

Output format: numbered sections matching the above, verbatim code blocks with file:line, then a single findings table at the end sorted by severity: # | severity | area | file:line | finding | reproduction. Do not propose or apply fixes. Do not modify anything.
